## 二、必须修复的问题（P1）

### P1-1 稳定性测试 heavy 用例指向错误素材，heavy 档位从未被覆盖

- `scripts/stability.py` 中 `ASSETS["heavy"]` 指向 `assets/test_offpitch_30s.wav`，该文件为 **light 档旋律重复 2 遍**生成，因此报告中 heavy 用例 5 轮结果与 light 完全一致（28.23→5.64 cents），heavy 档位（demo_heavy_30s.wav）从未进入测试。
- **复核澄清**（修正原报告的误判）：`demo_heavy_30s.wav` 本身生成正确。其"平均偏差 22.4 cents"是 heavy 档位设计值（±55–90 cents）经"到最近半音"映射后的理论结果——该指标数学上限为 50 cents，不能用来判定素材跑调程度；素材听觉跑调程度以设计档位 ±55–90 cents 为准，不存在"误生成或被覆盖"。

**修复建议**：
1. `stability.py` 的 heavy 用例改指向 `assets/demo_heavy_30s.wav`；
2. 重跑 5 轮更新 stability_report.json；
3. 预期结果：heavy 的 before_cents 约 20–30（到最近半音口径），修正后显著下降；±2 半音守卫作用于修正量（数学上 ≤0.5 半音），**不会**误拒，无需额外演练。

### P1-2 LLM 输出缺少 JSON Schema 校验（任务书 B6 明确要求"双层预检"）

`agent/intent.py` 的 `parse_intent` 只做了语义预检（preflight），`agent/schema.py` 里定义的 `CORRECT_PITCH_SCHEMA` **从未被用于校验 LLM 返回**。若 LLM 返回类型错误（如 `start_sec: "3"` 字符串），会在 preflight 的 `start < 0` 比较处抛 TypeError，被兜底成 500 而非清晰的 400。

**修复建议**：引入 `jsonschema`（纯 Python，无 GPU 依赖，符合选型底线），LLM 通道解析后先过 schema 再进 preflight：

```python
import jsonschema
jsonschema.validate(parsed, CORRECT_PITCH_SCHEMA["parameters"])  # 失败即降级规则模板
```

## 五、复核后排除的问题

> 原报告列为 P2-3，经代码与库行为复核后确认为**误报**，在此归档说明，不再作为修复项。

- **帧-样本对齐偏差（原 P2-3）**：`librosa.pyin` 默认 `center=True`，此时帧 i 的时间基准恰为样本位置 `i*hop_length`，与 `s*HOP_LENGTH` 切片**完全对齐，无偏移**。且原报告所述"偏 10ms"与按 `frame_length/2=1024` 样本计算的 23ms 亦不相符。结论：不存在该问题，无需修改 pitch.py 切片逻辑。
