# AI 音乐工作平台 · 黑客松参赛方案

> 暂定名：待定（建议贴合"人主导 + AI 辅助"理念命名）
> 参赛：Rebuild 黑客松 ｜ 定位：AI 赋能、人工为主的可编辑音乐工作平台

---

## 一、产品定位

**一句话定位**：一个以人工为主导、AI 为辅助的 AI 音乐工作平台——用户用自然语言表达想法，AI 生成可逐条确认、可编辑的修音操作序列，扒歌、生成、修剪、混音全部在统一节点画布中完成。

**核心理念**：
- 人工为主，AI 赋能：用户是创作者，AI 是提效助手，不做黑盒替代
- 过程可编辑：AI 先产出可解释的操作步骤，用户确认/修改/撤销后才渲染成音频
- 工作流统一：把散落在多个工具里的能力（扒歌、生成、剪辑、混音）收进一个画布

---

## 二、痛点与差异化

| 痛点 | 现状 | 我们的解法 |
|------|------|-----------|
| 工具割裂 | 扒歌用 UVR、生成用 MusicGen、剪辑用 DAW，流程断裂 | 统一节点画布，一条管线走完 |
| 黑盒不可控 | AI 一键修音准确率低、结果不可编辑 | 修音 Agent 产出可解释操作序列，人工逐条把关 |
| 门槛高 | 传统 DAW 学习成本高 | 自然语言表达想法，Agent 翻译成操作 |
| 无沉淀 | 修音经验无法复用 | 节点管线即模板，可保存复用 |

**对标差异**：TuneFlow 功能全但仍是传统轨道式交互；ComfyUI 有节点编排但无音频编辑体验；我们以"可编辑的自然语言修音过程"为差异化内核，直接呼应比赛"重构范式而非插件式改造"的哲学。

---

## 三、目标用户与典型场景

- 音乐爱好者：有想法但不会专业 DAW，想快速扒歌、改歌、混音
- 短视频创作者：需要快速出伴奏、修人声、加效果
- 独立音乐人：用 AI 提效重复劳动，保留创作主导权

典型场景示例：
> 用户导入一首歌 → 画布上 AI 自动扒成 人声/鼓/贝斯/其他 → 输入"副歌情绪推高一点，只把人声第 3 小节高音修准" → Agent 生成操作序列 → 用户确认后渲染，不满意可回退重来。

## 四、核心功能模块

### 4.1 AI 扒歌（音源分离）
- 基于 Demucs（htdemucs_ft），支持人声/鼓/贝斯/其他 4 轨分离
- 分离结果以节点方式进入画布，可单独静音、处理、重新融合

### 4.2 AI 音乐生成
- 集成 MusicGen（文本/旋律条件生成）作为生成节点
- 生成结果直接落到画布轨道，可继续修剪混音

### 4.3 节点式工作流画布（核心 UI）
- React Flow 构建，节点即操作（导入/扒歌/生成/分割/效果/混音/导出）
- 节点连线的顺序即处理管线，可回溯、可拖拽调整、可存为模板

### 4.4 音乐修剪与剪辑
- 波形可视化，时间轴选区裁剪、分割、拼接、淡入淡出
- 节点 + 时间轴双模式（参考 Audio Editor App）

### 4.5 混音
- 音量/声像/均衡/压缩/混响等效果节点
- 实时预览，参数可自动化

### 4.6 修音 Agent（智能中枢）
详见第五章。

### 4.7 工程管理
- 工程文件保存节点图 + 音频资产 + 修音操作历史
- 管线可存为可复用模板

## 五、修音 Agent 详细设计

**定位**：连接"自然语言想法"与"可编辑音频操作"的智能翻译层，是差异化的技术核心。

### 5.1 工作流程（plan-execute 模式）
```
用户自然语言想法
  → 意图解析（LLM）：识别目标（调情绪/修音准/对齐/去噪...）、作用对象、范围、参数
  → 生成操作计划（plan）：一条有序的音频操作步骤，映射到节点
  → 渲染为画布节点序列，返回给用户逐条确认
  → 用户可修改/删除/调整任一步骤参数，或对话式追问
  → 全部确认后执行渲染，输出音频
```

### 5.2 能力边界
- 支持的指令域：分离、分割、对齐、移调、时值、压缩、EQ、混响、音量自动化、去噪等
- 对话式澄清：想法模糊时追问（"你说的情绪推高是指音量还是混响？"）
- 多轮修改：确认后发现不对，可对话回退到任意步骤重来

### 5.3 状态机
`待解析 → 已生成计划（待确认）→ 部分修改 → 已确认（可执行）→ 已渲染 → 已回退`

### 5.4 与人工编辑的双向同步
- Agent 生成的节点序列=普通节点，用户可在画布上自由拖拽修改
- 用户手动改过节点后，Agent 感知状态，避免后续指令冲突

### 5.5 实现要点
- LLM 用 function-calling / tool-calling 把意图映射为结构化节点操作
- 节点执行参数用 JSON Schema 约束，保证 Agent 输出可被引擎执行
- 关键操作（如修音准）拆成"AI 检测偏移量 → 参数化校正"而非整段重生成，保证可控

## 六、技术架构

```
┌─────────────────────────────────────────┐
│ 前端层（Electron 壳 + React）            │
│  - React Flow 节点画布                    │
│  - 波形/时间轴编辑（WaveSurfer.js）       │
│  - 对话输入框（Agent 交互入口）            │
├─────────────────────────────────────────┤
│ Agent 层（修音 Agent）                   │
│  - LLM 意图解析 + tool-calling           │
│  - 操作计划生成 / 状态管理               │
├─────────────────────────────────────────┤
│ 音频引擎层                               │
│  - Web Audio API + Tone.js（实时预览）   │
│  - FFmpeg.wasm（裁剪/转码/拼接）          │
├─────────────────────────────────────────┤
│ AI 推理层（Python 独立 worker 进程）      │
│  - Demucs（扒歌）· MusicGen（生成）       │
│  - PyTorch / ONNX Runtime                │
│  - worker 隔离，不阻塞主音频引擎          │
├─────────────────────────────────────────┤
│ 数据层                                   │
│  - 工程文件（节点图 + 资产 + 操作历史）    │
│  - 本地文件存储                           │
└─────────────────────────────────────────┘
```

**架构要点**：
- AI 推理放独立 worker 进程（借鉴 Sounder），模型崩溃/加载不影响编辑
- Agent 层与画布层通过事件总线通信，节点图是唯一事实来源（single source of truth）
- 桌面用 Electron 封装（本地模型 + 本地文件，参赛演示稳定，不依赖网络与 GPU 云）

## 七、技术选型

### 7.1 前端画布与交互层

| 组件 | 主选 | GitHub 仓库 | 说明 | 备选 |
|------|------|------------|------|------|
| 前端框架 | React 18 | [facebook/react](https://github.com/facebook/react) | 生态最全，所有节点画布参考项目同栈 | Vue（对应 Vue Flow） |
| 节点画布 | React Flow | [xyflow/xyflow](https://github.com/xyflow/xyflow) | 节点式 UI 事实标准，Mecchi / Audio Editor App / Modulr 均用它，自定义节点、连线、拖拽成熟 | Svelte Flow（Svelte 技术栈用） |
| 波形/时间轴 | WaveSurfer.js | [katspaugh/wavesurfer.js](https://github.com/katspaugh/wavesurfer.js) | 成熟轻量，选区、区域标注、缩放、多轨渲染 | waveform-playlist |
| 状态管理 | Zustand | [pmndrs/zustand](https://github.com/pmndrs/zustand) | 轻量无样板，Modulr 同款，适合节点图+工程状态 | Redux Toolkit |

### 7.6 核心依赖清单

**前端（package.json）**：`react`、`@xyflow/react`、`wavesurfer.js`、`tone`、`@ffmpeg/ffmpeg`、`zustand`、`electron`

**Python worker（requirements.txt）**：`torch`、`demucs`、`audiocraft`、`transformers`、`ffmpeg-python`、`openai`（或 `requests`）

**运行时成本预估**：
- Demucs htdemucs_ft：推理建议 8GB+ 显存，无 GPU 可用 CPU（慢）
- MusicGen small：约 3GB 显存；medium 约 8GB；large 约 16GB
- 无 GPU 机器演示方案：预生成素材缓存，或现场用 CPU 小模型出短片段

## 八、MVP 范围与 48 小时排期

**MVP 必须包含**：
1. 可用的节点画布 + 音频播放/波形
2. Demucs 扒歌节点（真实可用）
3. 修音 Agent：自然语言 → 节点序列 → 用户确认 → 执行（至少支持 2~3 种指令，如"修音准""调音量""去人声"）
4. 基础修剪（裁剪/分割）+ 音量/均衡效果节点 + 导出
5. 一个完整 demo 场景

**排期**：
| 时间 | 任务 |
|------|------|
| Day 1 | 搭画布框架 + 音频引擎 + Demucs 接入 |
| Day 2 | 修音 Agent 接入 + 节点执行引擎 + 基础剪辑混音 |
| Day 3 | 打通 demo 全流程 + 录制路演视频 + 打磨 |

**可选加分项**（有时间再做）：模板保存、MIDI 转写、多轮对话回退。

## 九、风险与规避

| 风险 | 规避 |
|------|------|
| MusicGen 权重 CC-BY-NC（商用受限） | 参赛演示无碍；文档标注许可，后续可换开源权重 |
| GPU 依赖 | Demo 用小模型（MusicGen small 约 3GB）；无 GPU 机器演示可预生成素材 |
| 修音准确率兜底 | Agent 只做"参数化操作"而非整段重生成，结果可人工回退到任意步骤 |
| LLM API 成本/网络 | 演示时预缓存解析模板；可离线 fallback 到规则解析 |
| 48 小时工期紧 | MVP 收敛到 2~3 种核心指令 + 一条完整场景 |

## 十、参赛亮点总结

1. **可编辑的白盒修音**：把黑盒 AI 修音变成可逐条确认、可回退的可视化操作序列，呼应"人工为主、AI 辅助"
2. **统一工作流画布**：扒歌/生成/修剪/混音一条管线走完，填补"有生成无编辑"的空档
3. **人机协同范式**：自然语言表达 + 节点可视化，兼顾低门槛与专业可控
4. **真实可用**：Demucs/MusicGen 本地推理，demo 即真实产品形态
