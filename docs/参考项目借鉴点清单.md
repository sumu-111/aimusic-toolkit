# 参考项目 · 借鉴点对照清单

> 目的：研究材料，不是脚手架。clone 到 `references/` 仅供答辩引用与架构参考，

> 来源：github.com/tuneflow/tuneflow（MIT）、github.com/inoculate23/mecchi

## 一、TuneFlow（tuneflow/tuneflow，TS SDK，MIT）

| 借鉴点 | 具体实现 | 落到我们哪个任务 |
|--------|----------|-----------------|
| **插件只改数据模型，DAW 自动应用** | 插件 `init`/`run` 只操作 Song 对象，UI 自动刷新 | 印证核心设计"操作序列即数据"（答辩话术可直接引用） |
| **可回退管线（TuneflowPipeline）** | `addAsOrReplaceActivePlugin()`：可回退插件追加在当前位置后，不可回退则替换；维护 history + activePluginIndex，插入点之后全部移除 | 我们的**回退机制**：从已渲染节点 fork 新修改、不覆盖旧结果（后端 `render_and_export` 每次生成新产物文件，天然分支式） |
| **统一数据模型（models/）** | song/track/clip/note/tempo/time_signature/audio_plugin 分层建模 | 我们的 `project.json` 工程结构设计参考：nodes + analysis + history + version |
| **音高数学工具（utils.ts）** | `pitchToHz` / `midiNumberToPitch` 等频率↔音高换算 | 我们 `pitch.py` 的 `hz_to_semitones`/`cents_to_nearest_semitone`（已实现同类换算） |

**不借鉴**：TuneFlow 是完整 DAW 引擎 + 插件 SDK，面向专业用户；我们只做单条修音闭环，直接用它反而引入大量无关复杂度。

## 二、Mecchi（inoculate23/mecchi，Flask + React Flow）

| 借鉴点 | 具体实现 | 落到我们哪个任务 |
|--------|----------|-----------------|
| **节点注册表（backend 定义，前端渲染）** | `loader.py` 装配节点 → `GET /mecchi/init` 返回 `{nodes: [...]}` → 前端 palette 渲染节点面板 | 我们的**节点元数据上画布**：后端分析节点输出 JSON，前端 React Flow 渲染（对应"分析 JSON 对接前端"） |
| **前后端衔接方式** | Flask 后端 + React Flow 前端；上传接口 `/mecchi/upload` 存文件、`/out_data/<file>` 提供产物静态访问 | 印证我们的 worker 架构选型（Flask + 本地 output 目录）完全成立 |
| **节点参数化（config-based nodes）** | 节点由 `.py` 配置驱动，参数面板通用化 | 我们的**参数编辑面板**设计：plan 参数（起止时间/模式/强度/音阶）结构化定义后，前端可通用渲染 |
| **工作流画布组件（src-web/workflow）** | canvas/flow/node-base/palette/connection 组件划分 | 前端画布结构参考（前端 A 的事，这里只留档） |

**不借鉴**：Mecchi 核心是音乐**生成**（Audiocraft/AudioLDM，GPU + 大模型），与我们的"CPU 轻量修音"路线相反；它的音频管线对我们后端没有直接可复用代码。

## 三、对我们后端设计的三个验证结论

1. **worker 架构选型成立**：Mecchi 用 Flask + 输出目录 + 静态访问，我们同样的 Flask + `output/` 目录方案与主流一致，且天然兼容浏览器版 Plan B（CORS 已开）。
2. **回退设计有先例**：TuneFlow 的 pipeline 历史机制证明"操作序列 + 回退"是成熟模式，答辩时可对比"我们更轻：每次渲染即新文件，历史即文件列表"。
3. **数据驱动节点**：两个项目都印证"后端产出结构化 JSON → 前端通用渲染"是标准做法，我们的 analysis/plan/render_result 三个 JSON 契约是正确抽象。
